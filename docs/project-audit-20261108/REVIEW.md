# 项目审视：纸间 SourceReadSwift

## 结论

项目已经是功能面较完整的阅读器，覆盖小说、漫画、视频、有声、RSS、本地导入、书源管理、同步备份与诊断。当前最突出的问题是功能拼接后的生命周期复杂度与验收可信度：同一导航同时出现两套实现、屏外页面提前创建、后台预取无归属、短简介覆盖长简介，以及测试夹具自身给出误导信息。

建议把下一阶段重心放在稳定的“选书→开卷→跨章→返回→恢复位置”闭环、真实书源能力分级和错误恢复，暂缓继续叠加入口与设置项。刷新率配置、演示图片和单个源夹具通过都不能替代真实使用验收。

本轮分两块：用户九项问题的定点修复，以及解析/存储/工程结构的横向审查。生产 Swift 初始统计 319 个文件、90,746 行；`ReaderView.swift` 约 7,943 行、`JSCoreRuntime.swift` 约 5,725 行。该统计是范围清单，**不是逐行审完或所有线上源可用的证明**。旧 COVERAGE 的 pending 保持诚实，不批量改成已审。逐项发现以 NAVIGATION.md、READER.md、PARSERS.md 为准。

## 架构与产品点评

- 优点：原生 SwiftUI/UIKit/WebKit 结合适合多媒体阅读；网络/规则/存储已有不少独立模块；测试覆盖了真实 HTTP、磁盘、WebKit 和原生手势，基础设施比仅有 UI 的阅读器成熟。
- 主要维护成本：ReaderView 同时持有分页、滚动、缓存、朗读、菜单、跳转、持久化与手势状态；修一个章节边界容易牵动另一种模式。应沿“章节会话 / 内容预取 / 位置提交 / 渲染适配器”逐步拆分，保留现有行为回归后迁移。
- JSCoreRuntime 兼容层体积大，Android/Java 语义不能仅按函数名模拟。能力应按“原生支持 / 限定桥接 / 不支持”标注，导入时给出可诊断结果，而不是将所有 JSON 都显示为兼容源。
- 主题应有完整令牌、布局和纸面语言。本轮增加七套可选主题且保留原选择；下一步应让全部零散背景/边框收敛到同一语义层，避免主题只覆盖热门页面。
- 错误体验需要区分源规则不兼容、网站失效、登录/验证码、网络超时和空结果。空白正文或空列表不能成为通用失败界面。
- 依赖仅声明了版本区间，仓库未提交 `Package.resolved`；同一 SHA 在不同时间可能解析到不同依赖补丁版本。后续应从已验证构建产出锁文件再单独纳入，不在本轮凭猜测填写版本。
- 文档与工程存在版本漂移：README 仍以早期 MVP 为主要介绍，验证脚本依赖机器上的历史工具目录，部分源码契约测试绑死实现字符串。原生行为用例是主证据，源码契约只守范围与资源约束。

## 验证与限制

本机 Windows 无 iOS SDK，运行 Python/Swift 语法分析只能验证工具、资源与语法。必须以本轮同一 SHA 的 iOS 18/26 编译、测试与截图检查作为模拟器结论，再验证 device IPA。原生结果与最终桌面路径写入交付记录。

无法在当前环境证明真机持续 120 FPS、用户全部第三方书源可用、网络站点无未来变动或整个项目不存在其它 bug。该边界不取消本轮交付；它决定报告中哪些写“修复并回归通过”，哪些仍写“开放项/待真机验收”。
