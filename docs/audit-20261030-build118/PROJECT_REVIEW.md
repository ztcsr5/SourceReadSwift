## 结论先行

**你的担心有代码依据：阅读器已经不适合继续靠“加预加载、加底部留白、改等待时间”迭代。应该先收敛阅读内核的状态和版本契约，再逐项修复；但没有依据把整个项目推倒重写。**

最核心的冲突是：数据层判断“章内容是否变化”、分页层判断“页是否变化”、富文本层判断“需要重画吗”、控制器判断“需要更新邻页吗”，使用的不是同一套版本。于是可能出现：分页已经重算，显示仍是旧文本；章节已经加载，邻页仍是旧占位；后台已经预热，主线程仍同步分页。

本轮是**接手审查与证据整理**，不是修复交付：未修改业务 Swift、测试断言、project.yml 或工作流，未提交、推送、合并、重置分支，未删除原有备份。下面的机制由源码可证，具体设备症状仍须按验收矩阵复现。

## 三、阅读器实际执行链

| 用户模式 | 当前实际组件 | 说明 |
|---|---|---|
| 滑动 | `WebScrollReaderView` / WKWebView | 不是旧文档描述的 NativeReaderTextView 主路径 |
| 覆盖 | `CoverPageReaderView` → `CoverPageHostController` | 五槽位滚动宿主 |
| 平移 | 与覆盖相同的 `coverPagedReaderContent` | 当前没有独立区分覆盖/平移的渲染路由 |
| 仿真 | `CoverPageReaderView(turnStyle: .flip)` | 自定义旋转效果；不是当前未接入的 `pageCurlReaderContent` |

数据及事件链：章节载入/缓存 → `windowSections` → 章节分页缓存 → `pagedBlocksCache` → 页面富文本缓存 → 五槽宿主 → 手势提交 → 页/段/章节游标与进度持久化。工具栏、TTS、自动阅读、字体和安全区变化也会写入或影响这条链。

**先认清正在运行的路径，再决定保留/替换组件。** 不能因文件名包含 PageCurl，就把修它等同于修了用户正在使用的仿真模式。

## 四、优先级最高的机制问题

完整条目见 `ISSUE_REGISTER.md`；行号以当前 HEAD 为准。

1. **P1：重分页后可能复用旧正文。** `ReaderView:694-724,2866-2876` 的渲染 key 没有 viewport、内容 revision 或实际文本分片；`6716-6726` 在同 key 下直接返回旧 attributed string。旋转/容器高度变化后，第 0 页身份不变，但包含的文字已经变化。
2. **P1：中间段更新不会使章节缓存失效。** `ReaderView:778-780` 只看标题、段数、首段/尾段；`6480-6511` 据此复用旧页块。`[首,旧中,尾]` 与 `[首,新中,尾]` 确定具有同一签名，不是 hash 随机碰撞问题。
3. **P1：邻章准备好不等于邻页宿主更新。** `CoverPageReaderView.apply` 的更新门禁只看当前页和 revision，没有四个邻页 identity。当前页不变时，新邻页可能继续显示旧占位；离开当前页再回到它才碰巧刷新不是正确协议。
4. **P1：预热与同步分页职责冲突。** `ReaderView:6495` 令同步半径等于整个窗口；`6513` 缓存失效时仍同步进入 TextKit 分页，而重建由 MainActor 调度。窗口内的章节不满足“交给后台占位”的条件。118 扩大了网络书的同步半径；本地全窗口同步问题此前已存在。
5. **P2：位置锚点不足以应对重排。** 只有章号、段号、页序号，没有段内字符偏移；长段跨多页后换字号、旋转或切模式，不同恢复路径分别选该段第一/最后 continuation，无法保证同一阅读位置。

以上是源码合同缺口；用户可见的漏读、重复、卡顿需要真机/模拟器轨迹确认。独立 Python 模型已经验证签名等值、旧分片 key 不变、窗口内没有延后章节等事实，但模型不是 UIKit 运行结果。

## 六、全项目判断：保留资产，局部重整

### 保留，不与阅读器修复混做

- 书源规则/JSCore/网络兼容层与大量 fixture。它们仍有独立问题，但为翻页而顺便重写会扩大回归面。
- 书架、目录、TXT/EPUB 导入、持久化格式、下载和缓存数据。未来迁移必须单列兼容验收。
- 现有分页纯函数、geometry/policy 测试、signpost 与性能采样设施。补齐集成测试，不丢弃已有资产。
- 漫画、视频、音频、RSS 和 Web 写源等业务能力。

### 应重整的边界

- **ReaderSession**：唯一持有阅读锚点、当前页身份、session/content/layout revision、交互阶段和任务生命周期。
- **PaginationService**：输入不可变正文/排版快照；分页异步去重，产出带 source range 的不可变 PageLayout；拒绝旧 revision 回写。
- **RenderSurface**：只显示 PageLayout、上报 begin/cancel/commit；不自行决定加载章节或重算阅读位置。
- **Chrome/Settings/TTS**：独立状态，不让菜单、亮度、下载广播无关重建整个阅读内核。

这不是要求马上引入一套庞大新框架，也不是机械把 7,606 行拆成若干 extension。先修契约和失败测试，再分离状态所有权。

### 工程层的共同原因

旧交接文档落后几十个版本；旧渲染器与主路径并存且注释过时；AppState 转发许多无关 store 的全量变化；发布和测试是独立工作流；没有 Reader UI test target；依赖/工具链未完整锁定；同类修改在分叉提交中重复出现。它们会让不同协作者反复修局部现象，不必用“某模型不行”解释。

## 七、下一轮实施顺序与验收门槛

### A. 固定基线与失败样本

固定 HEAD、IPA hash、一个本地 TXT/EPUB、若干离线章节 fixture。建立问题编号、设备/系统/安装方式、稳定步骤、预期/实测和视频关联。先隔离网络慢，再验证网络异常。

### B. 优先补正确性，再优化性能

1. 为章节中段刷新、容器重排、邻页占位变正文写失败测试。
2. 统一 content/layout/render revision；稳定定位 identity 与渲染 key 分离。
3. 为每个文本块保留原始范围；字符锚点在重排后定位；正文拼回必须不丢不重。
4. 统一一次翻页事务和取消语义；等待补页不能靠猜固定延迟。
5. 把非必要章节分页移出主线程，in-flight 去重，再按性能数据决定窗口大小。不要先把缓存从 5 加到 10。
6. 明确覆盖/平移/仿真各自的产品语义，用同一会话合同接入；最后才清理旧代码。

### C. 发布阻断验收

| 类别 | 必测内容 | 通过条件 |

| 正文完整 | 长段、短段、emoji、中英混排、空行、图片、末章、inline标题，字号/行距/段距矩阵 | 源范围拼回原文；每个字符恰好一次；最终 glyph 全在 bodyRect 内 |

| 状态 | 目录/书签/进度跳转、字体/字号/旋转、切模式、前后台、退出重进 | 阅读锚点不漂移，旧异步任务不覆盖新会话 |
