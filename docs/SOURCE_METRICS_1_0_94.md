## 2. 两个数字的定义

### 天花板 56

```text
76 总条目 - 20 空壳 = 56 条“有规则池”
```

这 56 条是“最多可能绿”的上限，不是“56 条都能修好”。20 条空壳没有 `searchUrl / ruleSearch / ruleToc / ruleContent`，引擎再改也无规则可执行，所以不在 56 里。

### 引擎可修 46

当时的算法是：

```text
56 有规则池
- 5 个依赖外部/自建聚合服务（书山、聚合书库、聚合书源、圣灵、木里番茄）
- 3 个上游死亡站点（速读谷、有听网、集书阁）
- 2 个登录墙（少年梦、番茄四合一）
= 46
```

这 46 是“总绿色条数”的估算，包含原本已经 PASS4 的 10 条；不是“46 条失败项”。

## 3. 这个 46 的两处误差

### 误差一：按“名称”减，没有按“条目”减

书源库里有重名：

- `速读谷` 有 3 条（`sudugu.org`、`shudugu.org`、`sudugu.org#🐳`）；
- `得奇小说网` 有 2 条（空壳 `deqixs.co` + 可用 `deqixs.org`）；
- `聚合书源` 有 2 条（`聚合书源` + `聚合书源(zenneko)`）。

按名称减 1 个“速读谷”，实际漏掉 3 条失败条目；按名称减 1 个“聚合书源”，实际漏掉 2 条。按条目严格重算：

```text
登录墙            2 条
速读谷            3 条
有听网            1 条
集书阁            1 条
外部聚合服务      6 条（书山 1 + 聚合书库 1 + 聚合书源 2 + 圣灵 1 + 木里番茄 1）
顶点小说超时      1 条（150s，疑似站点死亡）
= 14 条非引擎阻断
56 - 14 = 42 条（严格口径约 42–44，取决于外部服务是否恢复）
```

所以 46 是乐观估算，条目级更接近 42–44。

### 误差二：报告早于 1.0.93

19:22 的报告跑在 1.0.92 之前的构建上。1.0.93 已修：

- `JSON.parse(result)` 按 Rhino 传当前对象 JSON 文本（含遇見 tocUrl、番茄APP 详情、七猫 toc）；
- `.length()` 重写限定 jsLib（连尚读书）；
- 1.0.92 的 relative URL 绝对化、`{{source}}` 插值泄漏。

这些修复会让报告里的部分 FAIL / FAIL_TOC / FAIL_DETAIL 变成 PASS，但**没有在真机上复测**，所以 46 既不是修复前的精确值，也不是修复后的值。
