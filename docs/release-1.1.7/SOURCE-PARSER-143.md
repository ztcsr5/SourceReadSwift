# Build 143：共享书源的 JavaScript 与本地数据链路

基线：`e31d58cd`（Build 142）。本轮只改书源引擎与测试，不改阅读器、界面、登录流程或数据结构。

## 输入与验证边界

- 输入为用户提供的 `shareBookSource (2).json`：1,189,932 字节，SHA-256 `92b8f1f3d0519bf4223378f3d17a37410d8eddff021fb2908b9d20a43e134ce3`。9 个不同的已启用书源，9 个均在搜索、详情、目录与正文阶段使用 JavaScript；5 个在这些阶段声明了内嵌 Base64 数据，7 个有详情初始化规则，8 个有登录 UI 字段。
- 仅在本机离线识别附件结构；不执行、不上传原始脚本，不访问其中的站点。测试以自写 JSON 和保留域名的本地响应重现规则形态。源码目录没有附件、真实登录凭据或第三方响应快照。
- 兼容性断言是引擎能运行相同规则形态，不等于 9 个真实源获得内容。需要外部网络、站方授权、账号、Android 宿主方法或源作者提供 iOS 适配的部分仍待单独验证。不会改变购买、登录、验证和访问权限。

## 修复与离线验收

| 断点 | 修复 | 检查 |
|---|---|---|
| `java.getString` 等默认解析原始页面，而非当前 JSON 条目 | 把选择器文档与中间 `result` 分开，按一次规则调用绑定，保留旧的页面回退 | 模板拼接后取条目标签；下一次脚本不能复用上次条目 |
| JSON 详情 `init` 解包后，脚本目录字段又被送进普通 URL 模板 | 用正常的 JSON 字段执行器接续初始化产物 | 搜索命中 → 详情标题变化 → 目录两章 → 分别得到两段不同正文 |
| `data:` 被当成 HTTP URL 修复，逗号和嵌入地址污染请求参数；非 HTTP 目录可能被按 host/path 过滤 | 本地内嵌地址保留外壳与负载，不走 HTTP 修复或 WebView；目录只用完整地址区分 | 纯 JSON 内含 URL 和 `method` 字段，仍按本地数据原样读；两章都保留 |
| Base64 编码不合法仍返回正常响应，MIME 丢失 | 按字节处理百分号、Base64 和 charset；限制解码大小，错误返回规则失败 | 百分号编码与大小写标记、MIME、损坏 Base64 |
| 正文响应的根是包含 JSON 文档的字符串时会展示原始 JSON | 有正文或初始化规则时先还原对象，再执行字段选择器 | 保留两章都必须提取到不同正文的原断言，另测显式包一层引号的响应 |
| 正文首句与章名共享前缀时，被去重器误删 | 完整标题按相等匹配，只有裸章节号允许带明确分隔符的短标题，并且不能把句子或唯一正文段当标题 | 保留「第一章的试读正文。」和短开头，继续删除「第8章 入城」这种真实重复标题 |

专门的 XCTest 是 `SourceParserBundleCompatibilityTests`，加入既有 `source-rows-probe.yml` 和 iOS 26 定向回归。CI 证据按实际最终 SHA 读取，不能用本说明替代测试结果。

[首轮原生回归](https://github.com/ztcsr5/SourceReadSwift/actions/runs/43731027934) 运行 167 项。搜索、详情、两条目录地址均通过；唯一失败用例是从两条目录打开正文，两条断言都返回了原始 JSON。此问题不能用打包成功替代；最终提交须重新通过原用例。

[第二轮回归](https://github.com/ztcsr5/SourceReadSwift/actions/runs/43733544699) 的引号包裹用例通过，但原端到端用例仍失败。输入诊断确认正文已是有效字典，不是字符串包裹。根因是 `ChapterTextSanitizer.normalize` 在「前缀相同且剩余不超过 12 字」时移除合法短句，随后 HTML 回退显示了原始 JSON。保留独立的包裹测试和原端到端用例，不改期望正文。
