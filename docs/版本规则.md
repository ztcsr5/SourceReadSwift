# 版本与发布规则

## 一、规则（自本轮起生效）

**每一次改动都升一个版本号**，即使只改一行文案：

| 字段 | 规则 | 示例 |
|---|---|---|
| `MARKETING_VERSION`（小版本） | 每次改动 **+1** | `1.0.30` → `1.0.31` → `1.0.32` |
| `CURRENT_PROJECT_VERSION`（构建号） | 每次改动 **+1** | `31` → `32` → `33` |

这样做的直接好处：设备上覆盖安装不会被系统当成“同一个版本”，出问题时能一眼对上「用户装的是哪一次构建」。

## 二、三处必须同步（少一处 CI 就红）

| 位置 | 作用 | 改什么 |
|---|---|---|
| `project.yml` | Plist 的唯一来源（CI 会断言 IPA 里的版本与它一致） | `MARKETING_VERSION`、`CURRENT_PROJECT_VERSION` |
| `SourceReadSwift/Shared/AppVersion.swift` | App 内展示（设置 → 关于纸间） | `minor`、`build` |
| `SourceReadSwiftTests/SearchURLResolverTests.swift` | 防止版本漂移的断言 | `AppVersion.minor`、`AppVersion.build`、`fullDisplayString.contains("Build …")` |

> `testAppVersionSemantics` 故意把数字写死：如果只改了 `project.yml` 忘了改 `AppVersion`，它会立刻失败。这不是重复劳动，是防漂移。

## 三、发布流程

1. 改代码；
2. 升版本（上表三处）；
3. 提交并推送；
4. 等两条 CI 绿：`iOS`（Build + 全量 XCTest）、`Unsigned IPA`；
5. 下载 artifact，落盘命名 `SourceReadSwift-<版本>-<提交短sha>.ipa`，例如 `SourceReadSwift-1.0.31-fixed-1a2b3c4.ipa`；
6. 记一行到下面的历史表。

## 五、踩过的坑：改文件必须保持 LF

1.0.31 的 Unsigned IPA 流水线在 `Summarize IPA artifact` 步骤失败，报：

```
Plist version: 1.0.31 (32)
::error::Version drift: Info.plist=1.0.31 (32) project.yml=1.0.31 (32)
```

两边看起来一致，实际是 `project.yml` 被写成了 **CRLF**：CI 里

```bash
VERSION="$(grep 'MARKETING_VERSION:' project.yml | awk '{print $2}' | tr -d '\"')"
```

`awk` 会把行尾的 `\r` 留在字段里，于是 `$VERSION` 实际是 `1.0.31\r`，跟 PlistBuddy 输出的 `1.0.31` 永远不相等。

**规则**：任何脚本化改文件都必须按二进制写回或用 `newline="\n"`；Windows 上 `open(path, "w")` 默认会把 `\n` 翻成 `\r\n`。仓库基线是 LF，改动后可以这样自查：

```bash
python -c "print(open('project.yml','rb').read().count(b'\r\n'))"   # 必须是 0
```

## 六、注意

- 版本号只增不减；补丁回退也要继续 +1，不要复用旧号。
- 文件名里的短 sha 用**实际构建提交**（不是文档提交），方便回溯 artifact。
- IPA 是未签名的：装到真机仍需自签或 TrollStore，与版本号无关。
- 构建失败、没有产出 artifact 的那一版，不算“已发布”，但版本号照样 +1（不回收），避免同名不同内容。
