## 5. 当前架构（B 方案）

### 5.1 结构

```
RootTabView
└─ ZStack
   ├─ navigationContent          ← 主页/寻书/设置/搜索，常驻，不销毁
   └─ ReaderOverlayLayer         ← AppState.readerOverlay 驱动
```

阅读器不再是 `NavigationStack` 的 destination。

### 5.2 为什么换

原实现里，手势一开始 SwiftUI 就拆掉 destination：

- destination 上的 `.toolbar(.hidden, for: .navigationBar/.tabBar)` 随之消失 → 主页 chrome 瞬切弹出
- `gateway.onDisappear` 触发 `releaseTabChromeHidden` → 底栏瞬切
- 主页 `onAppear` 跑投影刷新 → 书架重建

内嵌日志（`NavigationTrace`，20Hz 直接采样 UIKit）实证：

```
+ 4.122s  pop    willDisappear interactive=true isPop=true
+ 4.122s  chrome release ... owners=0 hidden=false
+ 4.215s  STALL  主线程停顿 61 ms
+ 4.227s  chrome acquire ... owners=1
+ 4.228s  pop    结束 cancelled=true
```

一次没滑够距离的侧滑，栏出现→消失闪一遍；同一序列在一次手势里重复 4 次。

### 5.3 相关文件

| 文件 | 职责 |
|---|---|
| `Features/Reader/ReaderOverlayLayer.swift` | 覆盖层视图、几何变换、遮罩、手势接线 |
| `Features/Reader/ReaderTransition.swift` | `ReaderTransitionPolicy`（纯函数）+ `ReaderTransition`（进度协调器） |
| `Features/Reader/ReaderCoverAnchor.swift` | 封面锚点采集、`readerPresentedAsOverlay` 标记、ready 信号收集 |
| `App/AppState.swift` | `readerOverlay`、tab chrome 所有权（含 350ms 挂起窗口） |
| `App/RootTabView.swift` | ZStack + 覆盖层挂载 |
| `Features/Reader/ReaderExitSwipeBridge.swift` | 左缘 `UIScreenEdgePanGestureRecognizer` |

九个阅读器入口（书架点书、详情「继续阅读」、详情章节、搜索书签、设置三处历史/统计）全部改为设置 `appState.readerOverlay`。

## 6. 手势（用户已确认"基本正常"，**冻结中**）

### 6.1 曾经的真实根因（已修，`dc7a26f7`）

**① `shouldBeRequiredToFailBy` 返回 true 给所有后代识别器。**
该方法语义是「我是否必须等对方失败」。返回 true 等于让边缘返回排队等 WKWebView 的 pan 失败；滚动 pan 通常要到手指抬起才失败，于是退出几乎起不来，只有 WebView pan 恰好快速失败（横向占优）时才偶然生效 → **"时灵时不灵"**。

**② `shouldBegin` 用瞬时速度判方向。** `.began` 时速度为 0 或噪声，随机拒绝。

修法：该回调对后代识别器返回 false；`shouldBegin` 不再看速度，方向改在 `.changed` 判（纵向占优放弃返回）；`shouldReceive` 收窄到左缘 32pt（**收窄**，保护正文横向翻页）。

### 6.2 约束

**不要为了修几何或白屏去动手势识别器。** 除非有证据证明两者直接依赖。

## 7. 两个当前 P0 故障（真机可复现）

### 7.1 进入：长时间白屏

**现象**（`1ad81b6d`，iPhone 13 Pro，5.17s 录屏逐帧）：

| 时间 | 画面 |
|---|---|
| 0–0.9s | 主页正常 |
| ~0.9s | 源封面消失 |
| 1.22–2.19s | **整屏纯白**，只剩一个灰色浮动按钮 |
| 2.19s | 正文出现 |

**已确认的机制**：遮罩在 `deadlinePassed(1.2s) && p≥0.62` 时撤除，而阅读器（WKWebView）此时尚未完成首帧绘制。所以白屏不是"等待久"，而是**遮挡撤得比首帧早**。

**第二个成因**：`request.coverImage` 来自 `readingCoverHandoff.frame(for:)`，该路径返回 `nil`，遮罩于是渲染 `Color(uiColor: .systemBackground)`——浅色模式下就是纯白。**没有封面图时，"等正文"必然表现为白。**

**未证实的部分**：不能排除 `ReaderView` 被重建（早期录屏出现过"正文先出现、随即消失"）。`1ad81b6d` 已加 `.id(request.id)` 与常驻遮罩来消除兄弟节点增减导致的重建，但真机仍白，说明主因是首帧时间，不是重建。

**建议修法**（未实施）：
1. 就绪信号改成**真实首帧**：WebView `didFinish` + 一次 `requestAnimationFrame` 回执，而不是 `hasResolvedOpeningPreview`。
2. 遮罩兜底色改成**阅读纸色**（`ReaderBackground` 实际纸色），不要 `systemBackground`。
3. 遮罩撤除绑定首帧信号，而不是时间截止。

### 7.2 退出：正文缩成左上角小纸片并被裁切

**现象**（`1ad81b6d`，3.41–4.39s）：正文缩成左上方一小页、内容明显裁切，然后主页恢复。

**尚未确证的根因**，两个可疑点：

1. **手算几何**。当前实现是：

```swift
let rect = ReaderTransitionPolicy.targetRect(cover: cover, screen: screen, progress: p)
let scaleX = rect.width / screen.width
let scaleY = rect.height / screen.height
...
.scaleEffect(x: scaleX, y: scaleY, anchor: .center)
.offset(x: rect.midX - screen.width / 2, y: rect.midY - screen.height / 2)
```

`scaleEffect` 以中心为锚缩放，`offset` 又在**未缩放坐标系**里平移，两者叠加后落点未必等于 `rect`。这是"缩到左上、还裁切"最可能的来源。

2. **坐标空间**。锚点用 `.global`（窗口坐标），覆盖层在 `GeometryReader` 内且 `.ignoresSafeArea()`，两者可能差一个安全区偏移。

**`coverRect` 的实际数值从未被记录**——日志只写了 `cover: ok/nil`。这是本轮诊断最大的缺口。

**建议修法**（未实施）：**删掉手算几何，改用 `matchedGeometryEffect`**。给定源视图与目标视图，系统自己完成位置/尺寸/圆角/裁剪插值，不存在缩放中心偏移。这也正是用户最初的要求。

## 8. 诊断设施

### 8.1 内置时间线（App 内，不依赖 Xcode）

设置 → 诊断 → 开发者调试 → **侧滑返回诊断 · 时间线**

- 20Hz 采样 `UINavigationController.isNavigationBarHidden` 与 `UITabBarController.tabBar.isHidden`，变化时记 `NAV` / `TAB`
- 记录 `pop` 转场（interactive / isPop / cancelled）、`chrome` 所有权变化、`shelf` 投影重建与耗时、`reader`/`detail`/`open` 生命周期、`route` 绑定翻转、`GEST` 手势状态、`overlay` 进度
- 主线程停顿 ≥80ms 会记 `STALL` 并附前 4 条上下文
- 分类筛选 + 一键复制

**这是本项目最有价值的产物，新接手者应继续用它取证。**

### 8.2 已埋但**不足**的点

`overlay` 日志目前只记 `p / ready / deadline / cover=ok|nil`，**没有 `coverRect`、`readerFrame`、`overlayFrame` 的具体数值**。下一位接手者第一件事应该是把这三个数值打出来：

```
overlay p=0.50 cover=(x,y,w,h) frame=(x,y,w,h) scale=(sx,sy) offset=(dx,dy)
overlay readerAppear=N readerDisappear=N
```

## 10. 已确认不可信的做法（血泪）

1. **不要把"编译通过"当成"交互完成"。** 编译通过 6 次，真机仍错 6 次。
