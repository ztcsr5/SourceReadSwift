## 六、第三轮：#12 的第一刀（先能测，再优化）

| 项 | 落点 | 说明 |
|---|---|---|
| 段落数组按指纹缓存 | `ReaderView.swift` `scrollModeParagraphs` + 文件私有 `ReaderScrollParagraphCache` | 滚动期间 body 会被反复求值，原来每次都把窗口内全部段落拼一份新数组（几百~上千段）。现在按 `bookID|内容指纹` 缓存，指纹不变直接复用 |
| 调试期滚动采样 | `NativeReaderTextView.swift` `scrollViewDidScroll` + `ReaderScrollPerfProbe` | DEBUG 包每 300 帧打印 `avg / worst`（毫秒），把「TextKit 回调慢」和「SwiftUI 重建慢」分开。Release 无任何开销（`#else` 空实现） |

### 为什么先不直接改 `allowsNonContiguousLayout`

`NativeReaderTextView.swift:90` 现在是 `false`（整篇强制布局）。把它改成 `true` 会让
`captureScrollAnchor` / `restoreScrollAnchor` / `scrollToParagraph` 里所有
`layoutManager.ensureLayout(for:)` 的语义跟着变（它们本来要求全量布局），
等于同时动「锚点、跳段、插图重排」三条最敏感的路径 —— 没有真机数字之前不该动。

### 真机测量协议（拿到数字再决定下一步）

1. Xcode 里以 Debug 跑真机，Console 过滤 `ReaderPerf`；
2. 选一个 3000 字以上的长章节，滑动模式连续快滑 10 秒，记录输出的 `avg / worst`；
3. 再滑到章界（触发下一章加载）重复一次；
4. 判定标准：
   - `avg < 2ms` 且仍然掉帧 → 瓶颈在 SwiftUI body 重建，下一步拆 `ReaderView` 的滚动子树；
   - `avg > 6ms` → 瓶颈在 TextKit 回调，下一步把 `updateVisibleParagraph` 的 `glyphRange(forBoundingRect:)` 换成分段缓存；
   - 只有章界卡 → 落实「滑动期间延迟重建」方案（`pendingRebuildConfiguration`，惯性结束再 `rebuild`），这是唯一会动到重建路径的改动，单独一轮做。
