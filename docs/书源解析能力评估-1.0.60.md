# 书源解析能力评估（v1.0.60）

> **结论先行**：书源解析不是“半开发”。搜索、详情、目录、正文、发现页五条主链，以及 CSS/Jsoup、XPath、JSONPath、`##` 变换、`@put/@get`、`<js>`、`jsLib`、`Packages` 兼容层、Cookie、GBK、分页、WebView 兜底、诊断报告都已经落地，并有 80+ 个书源相关 XCTest 文件覆盖。
>
> 真正的缺口集中在三处：**WebView 反爬语义（sourceRegex / webJs / overrideUrlRegex）**、**少量 Android Java 兼容类**、**XPath 与 JSONPath 的方言边界**。这三处会让“少数依赖 App API/强反爬的源”失败，但不代表主链不可用。
>
> 事实口径：只把仓库代码、XCTest、CI 日志写成“已完成”；没有真机/公网证据的写成“待验收”或 `NOT RUN`。

## 3. JavaScript 与 Java 兼容层

本项目不是“用 Swift 重写规则”，而是和栖阅同路线：**JavaScriptCore + Jsoup 原生桥 + `Packages` 仿真层**。

已暴露的高频 Java API（`JSCoreRuntime.swift` 内）：

- `java.lang`：`String`、`StringBuilder`、`Integer`、`Long`、`Boolean`、`Double`、`System`、`Thread`
- `java.util`：`ArrayList`、`HashMap`、`LinkedHashMap`、`HashSet`、`LinkedHashSet`、`TreeMap`、`Arrays`、`Collections`、`Objects`、`Base64`、`UUID`、`regex.Pattern`
- `java.io`：`ByteArrayInputStream`、`ByteArrayOutputStream`
- `java.net`：`URL`、`URI`、`URLEncoder`、`URLDecoder`
- `java.security`：`MessageDigest`、`Signature`、`KeyFactory`、`PKCS8EncodedKeySpec`、`X509EncodedKeySpec`
- `javax.crypto`：`Cipher`、`Mac`、`SecretKeySpec`、`IvParameterSpec`
- `java.util.zip`：`GZIPInputStream`、`InflaterInputStream`
- `org.jsoup`：`Jsoup.parse`、`Element`/`Elements`/`Document` 桥
- 宿主函数：`java.ajax`、`java.post`、`java.request`、`java.ajaxBytes`、`java.createSign`、`java.createAsymmetricCrypto`、`java.getVerificationCode`、`java.queryTTF`

原生桥规模：`LegadoHostServices.swift` 59 KB、`LegadoNativeBridges.swift` 63 KB、`JSCoreRuntime.swift` 278 KB。对应的 JS 兼容测试包括 `LegadoJavaCompatibilityTests`、`LegadoJavaScriptCompatibilityTests`、`LegadoNativeBridgeTests`、`RuleExtractorJSTests`、`SourceEngineBodyJSTests`。

栖阅在 56 KB 的 `packages_stub.js` 里额外提供了以下类；本项目当前未显式暴露：

| 栖阅类 | 典型用途 | 本项目状态 |
|---|---|---|
| `java.math.BigInteger` | RSA、大数运算 | 缺 |
| `java.nio.ByteBuffer` | 字节拼接、AES 入参 | 缺 |
| `android.text.TextUtils` | `isEmpty` / `join` | 缺 |
| `java.util.concurrent.TimeUnit` | `sleep` / 超时 | 缺 |
| `javax.crypto.SecretKeyFactory` + `DESKeySpec` | DES/3DES 源 | 缺 |
| `java.io.BufferedInputStream` / `InputStreamReader` | 流式解密 | 缺 |
| `java.lang.StringBuffer` | 老源字符串拼接 | 缺 |
| `android.graphics.BitmapFactory` | 图片尺寸/解码 | 缺（本项目走原生图像管线） |

注意：`Packages` 未实现的调用会被 Proxy 降级为空串并写 `bridge.error` 诊断（`JSCoreRuntime` 的未知 `java.*` 降级），所以症状常是“规则返回空”而不是“直接报错”。这也是用户觉得“半开发”的一个原因：错误被降级了，界面只看到空结果。

## 4. 真实缺口（按影响排序）

### P0-1：`sourceRegex` 的语义不是“正文清洗”，而是 WebView 资源嗅探

Legado 的 `BackstageWebView.kt` 里，`sourceRegex` 用于 `SniffingWebClient.onLoadResource`：当页面加载的子资源 URL 命中正则时，把该 URL 作为响应体返回。它不是 `ContentParser` 的清洗步骤。

本项目 `WebViewFallback.swift` 只做三件事：加载 URL、等页面完成、取 `document.documentElement.outerHTML`；没有资源嗅探。结果是：**正文/目录只在页面 XHR 里返回 JSON 的源，会拿到整页 HTML，规则自然匹配不到。**

`docs/书源字段兼容矩阵.md` 旧结论“把 sourceRegex 接进 HtmlRuleExtractor/ContentParser 做主链清洗”是**错误方向**，本次评估已纠正。正确实现是扩展 WebView 层。

### P0-2：`webJs` 没有注入 WebView

`SourceEngine.swift:801` 目前只把 `ruleContent.webJs` 当作“是否启用 WebView”的信号：

```swift
if let webJs = source.ruleContent?.fields["webJs"], webJs.contains("webView") { return true }
```

但 Legado 的 `BackstageWebView` 会在页面开始加载后执行 `webJs`（`loadUrl("javascript:...")`），用它改写 DOM 或取页面变量，再返回结果。本项目只返回原始 `outerHTML`，所以依赖 `webJs` 的源会失败。

### P0-3：`overrideUrlRegex` 未实现

Legado 用它在 WebView 内拦截跳转（订阅源迁移、广告跳转、章节页跳 App）。本项目 `WebViewFallback` 没有 `decidePolicyFor` 分支。

### P1-1：Java 兼容类缺口

见 §3 表。优先补 `BigInteger`、`ByteBuffer`、`TextUtils`、`TimeUnit`、`SecretKeyFactory`/`DESKeySpec`、`BufferedInputStream`/`InputStreamReader`、`StringBuffer`。

### P1-2：XPath 方言

`XPathRuleTranslator` 是“XPath → CSS”子集翻译，不是完整 XPath 引擎。以下写法需要真实 fixture 验证：`following-sibling::`、`preceding-sibling::`、`normalize-space()`、`contains()`、`position()`、`last()`、`text()` 组合、命名空间。遇到不能翻译的表达式时，应当**明确报诊断**，而不是静默空值。

### P1-3：`loginUi` 与 `ruleReview`

- `loginUi`：未实现，当前用 WebView 登录兜底。对“登录表单在 App 内、需要 JS 填表”的源体验差。
- `ruleReview`：未实现。Legado 3.x 有 `BookReview.kt`，属于书评扩展，不影响主阅读链。

### P2：语义待固定

- `nextContentUrl` 多值：当前只取第一页；需要 fixture 固定“数组/换行”行为后合并。
- `replaceRegex` 合并顺序：单 URL 与多页合并后的替换范围需要 fixture。
- `downloadUrls`：刻意不消费，避免死按钮；实现前提是完整下载队列。
- `sourceRegex` 旧文档错误：本次已在新文档纠正，旧文档保留历史但标注“已纠正”。

## 5. 为什么 iOS 的 JSON 书源生态“少”

不是技术不可行，而是四个现实约束：

1. **App Store 审核**：书源聚合类应用容易被 5.2/4.2 拒审，很多产品只做 TestFlight、企业签或侧载。
2. **站点漂移**：书源是“站点契约”，站点一改版就失效；维护成本高于一次性开发。
3. **Android 生态惯性**：Legado 的 Rhino/Java API 在 Android 上是“原生就有”，iOS 需要仿真层，移植门槛高。
4. **商业意愿**：成熟产品（栖阅、香色闺阁、源阅读、源阅）大多闭源，避免书源版权与审核风险。

已知的 iOS 同类产品：栖阅、香色闺阁、源阅读、源阅、益达（Flutter 壳，非书源引擎）、开元阅读（Flutter + 自研规则引擎）。其中栖阅和开元是当前最强的两个参照。

## 6. “完美兼容”为什么难，但可以分级验收

Legado 书源不是静态 JSON，而是“JSON + 选择器方言 + JS/Java + 网络 + WebView”的组合协议。难点按层拆：

| 层 | 难点 | 本项目状态 |
|---|---|---|
| JSON | 字段缺失、类型漂移（bool/string/number） | 已用 LosslessJSONValue 兼容 |
| 选择器 | CSS/Jsoup/XPath/JSONPath 四套方言 | CSS/JSON 强，XPath 子集 |
| JS | Rhino 语义、Java 包、同步 ajax | JSC + Packages 层，覆盖高频 |
| 网络 | POST、Header、Cookie、GBK、压缩、代理 | 完成 |
| 反爬 | Cloudflare、验证码、WebView、资源嗅探 | 部分：无 sourceRegex/webJs/overrideUrlRegex |
| 站点 | 改版、登录态、限流 | 只能靠持续体检，不能“一次做完” |

建议把“完美”拆成四级：

- **L1 能导入、能搜索**；
- **L2 能详情、能目录、能正文**；
- **L3 能处理 JS/加密/分页/图片**；
- **L4 能处理 WebView 反爬与 App API 源**。

当前主链在 L1–L3；L4 是下一阶段的明确目标，不是“未知的半成品”。

## 7. 补齐路线（可验收）

### S1（P0）WebView 语义对齐

实现：

1. `WebViewFallback.load(url:delay:javaScript:sourceRegex:overrideUrlRegex:)`；
2. 注入 `webJs`（`evaluateJavaScript`，兼容返回字符串/JSON）；
3. 资源嗅探：注入 XHR/fetch/PerformanceObserver 钩子，命中 `sourceRegex` 后用带 Cookie 的 URLSession 取资源体；
4. `overrideUrlRegex` 在 `decidePolicyFor` 中拦截并返回空响应。

验收：

- 本地 HTML fixture：页面 XHR 返回 JSON → `sourceRegex` 命中 → 规则解析出书名；
- `webJs` fixture：脚本改写 DOM 后返回指定字符串 → 正文匹配；
- 模拟器 XCTest + 真机手工各一次。

### S2（P1）Java 兼容类补齐

按 §3 表逐个加，全部走 `JSCoreRuntime` 的 `Packages` 层；每个类至少一个 `LegadoJavaCompatibilityTests` 用例；用 `legado-capability-bank-20260908.json` 做回归。

### S3（P1）XPath/JSONPath 方言冻结

从真实书源中抽 20 条 XPath/JSONPath，做成脱敏 fixture；不能翻译的表达式输出 `bridge.error` 诊断，不再静默空值。

### S4（P2）真实源健康度

- 30 个真实源，按 搜索/详情/目录/正文 四阶段跑；
- 结果只做日报，不阻塞 CI；
- 失败按 `stage + JS error + HTTP + rule` 分类，进入 `SourceDiagnosticRepairAdvisor`。

### S5（P2）用户体验

- 书源列表显示“最近一次体检”的健康徽章；
- 失败详情直接给出“哪一步、哪条规则、什么错误”；
- 一键套用修复建议（已有 `SourceDiagnosticRepairAdvisor` 基础）。

## 9. 一句话回答用户

- **“书源解析能力怎么样了？”**：主链完整，L1–L3 可用；缺口是 WebView 反爬三件套、少量 Java 类、XPath 方言和真实源回归，不是“只能解析一半”。
- **“iOS 上 JSON 完美兼容难吗？”**：难在 Rhino/Java 语义与 WebView 反爬，不在 JSON；栖阅已经证明 JSC + Jsoup + Packages 路线可行，本项目走的是同一条路，剩下的是覆盖度与验收工程。
